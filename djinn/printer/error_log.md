## 2026-05-23 — Software root cause identified + fixes applied

### Root cause
The failures were **primarily a software tolerance issue**, not hardware damage:

1. **verify_heater too tight:** Default `check_gain_time:30` means Klipper declares a heater fault if it can't confirm temp within 30 seconds. The nozzle_mcu serial line experiences brief EMI spikes during printing (from stepper motor switching noise). These spikes cause momentary thermistor reading loss. With a 30s window, even a 1-2 second reading gap triggers key564 and kills the print.

2. **PrusaSlicer gcode fan ramp:** The cup gcode (`cup_geometry_klipper_patched.gcode`) was generated by PrusaSlicer 2.9.4. PrusaSlicer ramps the part cooling fan to ~61% (`M106 S155.55`) right at the brim-to-first-perimeter transition (line ~1971, ~19.5mm filament used). The Creality slicer keeps the fan completely off (`M106 S0`) for the entire first layer, then turns it on after. The fan turn-on creates an EMI spike that disrupted the nozzle_mcu at exactly that point — every time, deterministically.

3. **Missing preheat in cup gcode:** Benchy (Creality slicer) starts with `M190 S60` + `M104 S210` before `START_PRINT`, pre-warming everything. Cup gcode starts with `M140 S0` + `M104 S0` — turns everything off immediately, making START_PRINT do all the heating from cold, which takes longer and puts the verify_heater in a more stressed state.

### Evidence
- All cup failures at identical `print_duration=5.3s`, `filament_used=19.5mm` — hardware EMI is random, deterministic failures = specific gcode command
- Benchy (14 min, 185 layers) ran with `retx=0, inv=0` the entire print on same hardware
- Hotend temp held ±0.6°C throughout Benchy — hardware is healthy

### Fixes applied

**1. printer.cfg — verify_heater relaxed:**
```
[verify_heater extruder]
check_gain_time: 120    # was 30
max_error: 999          # was default (~120)
hysteresis: 20          # was default (~5)
```

**2. New gcode file: `cup_geometry_creality_fixed.gcode`**
- Added preheat before START_PRINT (matching Creality slicer style):
  ```
  M190 S60          ; wait for bed
  M104 S215         ; start heating hotend
  M82               ; absolute extrusion mode
  M140 S0
  M104 S0
  START_PRINT EXTRUDER_TEMP=215 BED_TEMP=60
  M900 K0.042000    ; pressure advance
  ```
- Replaced early fan ramp (`M106 S155.55`) with `M106 S0` for first layer — fan stays off during brim/layer 1, matches Creality behavior

**3. Config backup:** All printer configs saved to `~/Obsidian/djinn/printer/backup/`

**4. Benchy trace log:** Full per-layer print trace saved to `~/Obsidian/djinn/printer/benchy_trace.md`

- **Status:** Fixes applied. Cup print queued as `cup_geometry_creality_fixed.gcode`.

| `key561` instant 0→100% retransmit | grep M106 in gcode at failure Z height | Fan EMI spike (M106 S255 at bridge infill) — cap fan at S128 in gcode or PrusaSlicer settings |
| `key561` gradual retransmit climb | nozzle_mcu retransmit_seq + XY in TRACE log | Physical cable issue — reseat or reroute |

| `klippy_disconnect` random timing | `leveling_mcu` or `nozzle_mcu` retransmit_seq climbing | Physical cable issue — reseat or replace |
| `bytes_invalid` in stats | Signal integrity | EMI / damaged cable shielding — not a connector issue |

| Print starts but stalls in START_PRINT | `print_duration=0` for >5 min | Heating or leveling stall — check temps and leveling_mcu |

## Diagnostic Protocol — Print Failure Triage (added 2026-06-02)

**When any print fails mid-run, follow this order. Do not skip steps.**

### Step 1 — Run djinn-print-tracer on the next attempt
```bash
djinn-print-tracer --interval 5 &
```
Watch for:
- **Instant 0→100% retransmit** → EMI event from a gcode command → go to Step 2A
- **Gradual retransmit climb** → possible hardware → go to Step 2B

### Step 2A — Gcode first (instant failure pattern)
```bash
grep -n "M106" /path/to/failing.gcode
# Find the line near the failure Z height
# Cap any M106 S255 → M106 S128
sed -i 's/^M106 S255$/M106 S128/' failing.gcode
```
Re-upload and retry. If it passes → done. Never touched hardware.

### Step 2B — Run the calibration cube before touching any hardware
```
Print: CRtestcube_Ender-3 V3 Plus_26m.gcode  (already on printer)
```
- **Cube passes** → hardware is fine. Problem is in the failing gcode. Grep M106, check START_PRINT sequence, check object placement on bed.
- **Cube fails** → hardware issue confirmed. Then check cables, connectors, strain gauges.

### Why the cube
- Creality slicer: no `M106 S255` during print, no bridge fan spikes
- Centered at Y=135–165: doesn't stress cable at extreme bed positions
- 26 min: long enough to catch thermal/EMI drift
- Already on the printer — no upload needed

### Rule
> If the print survives the first 30 seconds, the start position is not the problem.  
> Consistent failure duration = gcode command. Random failure duration = hardware.
