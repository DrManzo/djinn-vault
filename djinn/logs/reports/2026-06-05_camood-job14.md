## Observed Issues

### Issue 1 — First stop at 10min (0.4% progress)
**What happened:** Print auto-paused at ~10 minutes in, then went to `standby`. Javier saw error `E0003：key2561 communication abnormal` on the printer's physical LCD screen.
**Root cause CONFIRMED (klippy.log 15:34:00):**
```
Timeout with MCU 'nozzle_mcu'
Transition to shutdown state: {"code":"key561","msg":"Lost communication with MCU 'nozzle_mcu'"}
```
Klipper hard-shutdown due to nozzle_mcu UART communication timeout. The toolhead MCU (nozzle_mcu) lost serial connection with the main board. Klipper kills all motion and goes to shutdown when this happens, which surfaces as "paused → standby" in Moonraker.

**This happened 3 times today:**
- 14:24:21 — Lost communication with MCU 'nozzle_mcu'
- 14:31:33 — Lost communication with MCU 'nozzle_mcu'
- 15:34:00 — Lost communication with MCU 'nozzle_mcu' (job14)

**Why during first layer:** `START_PRINT` runs a full bed leveling mesh probe (20+ point grid across the full bed). That wide XY sweep at Z=0 stresses the nozzle_mcu cable bundle enough to drop the UART connection.

**Root cause is the cable:** The nozzle_mcu cable bundle has insufficient slack or routing relief. Wide XY travel (especially during bed leveling or 3× plate prints spanning X=27–273mm) pulls or kinks the cable. This is a hardware issue — not filament, not gcode, not height alone.

**Fix required:** Physical re-route or cable relief on the nozzle_mcu harness so it has slack in all XY positions at all Z heights.

### Issue 2 — Speed at 20% after restart
**What happened:** After Javier restarted from Fluidd (resume, not full restart), speed came up at 20%. Javier manually ramped 20% → 50% → 75% → 100% over ~25 seconds.
**Root cause:** `M220 S100` in `start_gcode` only runs on a **fresh print start**, not on a resume. When Javier resumed from Fluidd the start_gcode was not re-executed. The 20% may have been a persistent override from a previous run or a Fluidd default on resume.
**Fix needed:** The `djinn-gcode-safety` pipeline should inject `M220 S100` at the very first layer change (Z=0.2mm) so it re-applies regardless of resume state. OR: add `M220 S100` to the Klipper `RESUME` macro on Calliope.

### Issue 3 — Z too low after first restart
**What happened:** After the restart, Z position was reading low. Javier noted this as a problem with first-layer height after resume.
**Likely cause:** On resume from `standby` (not `paused`), Klipper may not re-home or re-apply the Z offset. A full standby → print cycle skips the bed leveling mesh that `START_PRINT` runs on fresh start.
**Fix needed:** Always do a fresh print start (not resume from standby) after a `standby` state — or ensure `START_PRINT` macro re-runs bed leveling on resume after standby.

### Issue 4 — Second pause (15:42) — printer safe-park behavior
**What happened:** Printer paused, nozzle lifted up and away from object (not guided by Javier), then after a couple seconds resumed fine.
**Assessment:** This is Klipper's standard `PAUSE` safe-park macro working correctly — lifts nozzle to a safe Z, moves to park position, waits for resume. Behavior was correct and expected.
**Status:** No issue — working as designed.

## Technical Decisions

**M220 S100 in start_gcode vs inline gcode — Why:** The start_gcode fix (added to printer profile) resets speed on fresh print starts. But it doesn't cover resume-from-standby. The more robust fix is to also inject `M220 S100` at the first layer change in the gcode itself (via `djinn-gcode-safety`), so the reset is always present in the file regardless of how Klipper invokes it.

**djinn-print-monitor zone guard (first_layer_seen) — Why:** At monitor startup, the toolhead is often parked at a high Z from a previous print (e.g. Z=330.8mm, Z=164.8mm). Without this guard, all zone alerts fire immediately as false positives and don't re-fire when the print actually reaches those heights. The guard requires Z ≤ 5mm before enabling zone tracking, confirming the first layer started.
