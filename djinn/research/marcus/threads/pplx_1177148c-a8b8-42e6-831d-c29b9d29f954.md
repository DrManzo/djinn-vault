2. filament_used Accuracy: Is It Enough?

Short answer: It's sufficient for inventory tracking but not analytically precise. Klipper's print_stats.filament_used reports in millimeters of filament extruded — not grams. The conversion to grams requires density (g/cm³) and diameter (1.75mm standard):

For automatic inventory deduction: Spoolman's Moonraker integration handles the mm→grams conversion automatically using the spool's registered density and diameter. After setup, every completed print deducts from the correct spool with no manual entry. Weight-based confirmation (a scale + load cell) is only necessary if you're tracking remnant spool weight for near-empty alerts — for standard inventory deduction in a commercial PLA operation, Spoolman + filament_used is production-proven.

Automation Gap Analysis & Closure Plan

This is a direct response to your four-gap breakdown, grounded in the Moonraker documentation and your existing Djinn/Salomon stack. Here's what each gap actually is, and how to close it.

Gap 1: Queue-Tracker Bridge

Root cause: djinn-print-track subscribes to print_stats via WebSocket and writes to prints.json — but Moonraker's job queue (print-queue.json) is a separate API surface with its own state machine. They share no wire between them.

The Moonraker [job_queue] API has four states: ready, loading, starting, and paused. The bridge logic is straightforward: when print_stats.state transitions to printing, query the queue status to match the filename, then synchronize records bidirectionally.
moonraker.readthedocs

Implementation — queue_bridge.py (add to djinn-print-track or as a sibling service):

python
import asyncio, json, websockets, requests, time
from pathlib import Path
from datetime import datetime

MOONRAKER = "http://localhost:7125"
WS_URL    = "ws://localhost:7125/websocket"
QUEUE_FILE = Path("print-queue.json")
PRINTS_FILE = Path("prints.json")

# Filament: mm → grams for PLA+ (density 1.24 g/cm³, diameter 1.75mm)
def mm_to_grams(mm: float, density=1.24) -> float:
    radius_cm = (1.75 / 2) / 10
    return mm * 3.14159 * (radius_cm ** 2) * density

async def monitor():
    async with websockets.connect(WS_URL) as ws:
        # Subscribe to print_stats
        await ws.send(json.dumps({
            "jsonrpc": "2.0", "method": "printer.objects.subscribe",
            "params": {"objects": {"print_stats": None}}, "id": 1
        }))
        current_job = {}
        async for raw in ws:
            msg = json.loads(raw)
            stats = (msg.get("params", {}).get("status", {})
                       .get("print_stats", {}))
            if not stats:
                continue

            state = stats.get("state")

            if state == "printing" and not current_job:
                filename = stats.get("filename", "")
                current_job = {
                    "filename":   filename,
                    "started_at": datetime.utcnow().isoformat() + "Z",
                    "state":      "printing",
                    "job_id":     _find_queue_job(filename)
                }
                _upsert_queue(current_job)

            elif state in ("complete", "error", "cancelled") and current_job:
                current_job.update({
                    "state":          state,
                    "completed_at":   datetime.utcnow().isoformat() + "Z",
                    "total_duration": stats.get("total_duration", 0),
                    "print_duration": stats.get("print_duration", 0),
                    "filament_mm":    stats.get("filament_used", 0),
                    "filament_grams": round(mm_to_grams(
                                        stats.get("filament_used", 0)), 2),
                })
                _finalize_record(current_job)
                _generate_print_dir(current_job)
                current_job = {}

def _find_queue_job(filename):
    r = requests.get(f"{MOONRAKER}/server/job_queue/status")
    for job in r.json().get("result", {}).get("queued_jobs", []):
        if job["filename"] == filename:
            return job["job_id"]
    return None

The bridge subscribes once and reacts to state transitions — no polling. The mm_to_grams() function uses the Klipper-documented density formula from the filament_used field, which reports in millimeters.

def deduct_filament(grams_used: float):
    inv = json.loads(Path("filament_inventory.json").read_text())
    active = next((s for s in inv["spools"] if s["loaded"]), None)
    if not active:
        return
    active["remaining_g"] = round(active["remaining_g"] - grams_used, 2)
    active["last_used"] = datetime.utcnow().isoformat() + "Z"
    # Alert check
    if active["remaining_g"] < active["low_threshold_g"]:
        send_telegram(f"⚠️ LOW FILAMENT: {active['color']} {active['material']} "
                      f"— {active['remaining_g']}g remaining")

Gap 4: Creality Print ↔ Moonraker State Machine

This is the most important finding from the official docs. The complete print_stats.state machine is:
moonraker.readthedocs

State	Meaning
standby	No job loaded — printer idle after boot OR after SDCARD_RESET_FILE
printing	Virtual sdcard actively processing a file
paused	Job is paused (M600, user pause)
complete	Last job finished successfully
error	Last job exited with error
cancelled	User cancelled

What happened with your Terp Tribe print: Creality Print uploaded the file via the OctoPrint compat layer (POST /api/files/local) and issued a start command. During bed heating before actual extrusion, the state was standby because print_stats only transitions to printing when the virtual sdcard begins actively streaming the file — not when heaters are activated. Klipper's idle_timeout state would have shown Printing (since heaters count as activity), but print_stats.state stays standby until M24 equivalent actually starts.

Reliable heuristic for Creality Print detection — watch both objects:

python
# Subscribe to BOTH objects to catch the full Creality Print sequence
await ws.send(json.dumps({
    "jsonrpc": "2.0", "method": "printer.objects.subscribe",
    "params": {"objects": {
        "print_stats": None,
        "virtual_sdcard": None,   # is_active + file_path = reliable pre-print indicator
        "heater_bed": None,       # bed heating = Creality Print prep phase

}))

The correct detection sequence for Creality Print:

text
1. virtual_sdcard.file_path becomes non-null   → file uploaded, prep starting
2. heater_bed.target > 0                        → Creality Print heating phase ("standby" in print_stats)
3. virtual_sdcard.is_active == True             → actual print stream started
4. print_stats.state == "printing"              → CONFIRMED printing (write job_start record here)
5. print_stats.state == "complete"              → finalize

The tracker's heuristic worked because it caught step 4. The "standby during bed heat" was expected behavior, not a bug — it just means you should not use print_stats.state == standby + bed temp > 0 as a "print starting" signal. Use virtual_sdcard.is_active == True as the pre-print warning, and print_stats.state == printing as the authoritative job-start trigger.
